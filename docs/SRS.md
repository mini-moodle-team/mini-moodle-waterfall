## 1. Introduction

### 1.1 Product Scope（產品範圍）

Mini Moodle 是一個網頁版的課程管理系統，提供教師與學生在同一個平台上管理課程、發布公告、討論與繳交作業。

**本系統包含以下八項功能：**

| # | 功能 | 使用者 | 對應決定 |
| --- | --- | --- | --- |
| 1 | 註冊 | 教師、學生 | D-01 ~ D-04 |
| 2 | 登入 | 教師、學生 | D-00a、D-05 |
| 3 | 建立與管理課程 | 教師 | D-06 ~ D-08、D-10 ~ D-12 |
| 4 | 以課碼加入課程、退出課程 | 學生 | D-09、D-12 |
| 5 | 課程成員 | 教師、學生 | D-13 ~ D-15 |
| 6 | 公告 | 教師發布，學生查看 | D-16 ~ D-18 |
| 7 | 留言板 | 教師、學生 | D-19 ~ D-21 |
| 8 | 作業 | 教師建立與批改，學生繳交 | D-22 ~ D-28 |

**本系統不包含以下功能（列為未來功能）：**

| 功能 | 對應決定 |
| --- | --- |
| 寄送 Email（含 Email 登入、忘記密碼） | D-00a、D-00b |
| 教師驗證機制（例如教師驗證碼） | D-01 |
| 助教（TA）角色 | D-02 |
| 協同教師（一門課多位教師） | D-11 |
| 線上測驗、系統管理員後台、行事曆、私人訊息、學期成績總表 | D-29 |
| 中英文介面切換 | D-30 |
| 手機版介面 | D-31 |

### 1.2 Product Value（產品價值）

- 提供教師與學生共同使用的線上課程平台，讓課程資訊集中在同一個地方
- 教師可以建立課程、發布公告傳遞資訊，並出作業與批改，不需另外透過通訊軟體或 Email
- 學生輸入課碼即可加入自己修習的課程，並在課程頁查看公告、作業與成績
- 留言板讓課程相關的問題集中在課程內討論，教師與同學都看得到

### 1.3 Intended Audience（目標使用者）

| 使用者 | 說明 |
| --- | --- |
| 教師（Teacher） | 開設課程的人，註冊時選擇「教師」身分，以教職員編號作為帳號 |
| 學生（Student） | 修課的人，註冊時選擇「學生」身分，以學號作為帳號 |

每個帳號只能是教師或學生其中一種身分，註冊後不能更改（D-01、D-02、D-03）。本系統沒有系統管理員角色（D-29）。

### 1.4 Intended Use（預期用途）

**教師**

1. 註冊、登入
2. 建立課程，系統產生課碼後提供給學生
3. 編輯課程資訊、暫停課碼、查看成員名單、手動加入學生
4. 發布、編輯、刪除公告
5. 在留言板發言，並可刪除不當留言
6. 建立、編輯、刪除作業，查看繳交狀況、批改並發布成績

**學生**

1. 註冊、登入
2. 輸入課碼加入課程；加錯時可以自行退出
3. 查看公告、成員名單與課碼，可將課碼提供給尚未加入的同學
4. 在留言板發言，編輯或刪除自己的留言
5. 上傳作業檔案，可重新繳交（截止後視為遲交），並在教師發布後查看成績與評語

### 1.5 General Description（整體描述）

Mini Moodle 參考學校使用的 Moodle 系統，保留其最核心的課程功能。系統以網頁形式提供，介面為中文，只支援桌上型電腦瀏覽器（D-30、D-31）。帳號由使用者自行註冊，系統不寄送任何 Email（D-00a）。

需求衝突的處理原則為「實作最簡單、先做出可用系統」，詳見需求決定表 `docs/elicitation-notes/decision-table.md`。本系統與 Agile 組開發相同的八項功能範圍，但詳細需求由兩組各自決定。

## 2. Functional Requirements（功能需求）

- 每條需求只描述一件事，並寫出來源
- 「課程成員」指該課程的教師及學生，其他名詞定義見第 6 章
- 來源寫「補充」的是問卷沒有直接問到的項目（多為錯誤處理或邊界情況），由 AI 起草、RA 確認後保留
- 優先度：來源為決定表或功能描述者為 High；補充則由RA決定

### 3.1 User Interface Requirements（使用者介面）

#### UI-01 共通介面規則

- 系統主要介面應使用中文（D-30、NFR-COM-02）。
- 系統以桌上型電腦瀏覽器為本版目標；手機版介面不在本版範圍內（D-31、NFR-COM-01）。
- 只有已登入使用者可以存取註冊頁、登入頁以外的頁面（FR-2.5）。
- 只有課程成員可以進入單一課程的頁面（FR-4.7）。
- 欄位輸入無效時，介面應顯示與該錯誤對應的訊息；訊息內容依第 2 章各 FR 定義。

#### UI-02 註冊頁

註冊頁應提供帳號、密碼、確認密碼、姓名及身分欄位。身分選項只有「教師」與「學生」。頁面應提供註冊操作。登入頁入口的位置屬介面設計，由 SD 決定。

發生下列情況時，頁面應拒絕註冊並顯示第 2.1 節指定的訊息：

- 密碼不符合 NFR-SEC-01。
- 密碼與確認密碼不一致。
- 帳號已被註冊。
- 必填欄位空白。

註冊成功後應導向登入頁。對應需求：FR-1.1～FR-1.8。

#### UI-03 登入頁

登入頁應提供帳號、密碼欄位及登入操作。登入失敗時只顯示「帳號或密碼錯誤」，不得指出是哪一項錯誤；登入成功後導向課程列表頁。註冊頁入口的位置屬介面設計，由 SD 決定。對應需求：FR-2.1～FR-2.5。

#### UI-04 課程列表頁

課程列表頁應列出使用者所屬的全部課程：教師看到自己建立的課程，學生看到已加入的課程。建立課程及以課碼加入課程的入口位置屬介面設計，由 SD 決定。對應需求：FR-3.1、FR-3.9、FR-4.1。

#### UI-05 建立與編輯課程介面

建立課程介面應提供課程名稱、課程說明及系所代碼欄位。系所代碼不是兩個大寫英文字母時，介面應拒絕建立並顯示原因。建立成功後應顯示系統產生的課碼。

課程編輯介面應只允許該課程的教師修改課程名稱及課程說明。對應需求：FR-3.1～FR-3.7。

#### UI-06 課程頁

課程頁應顯示課程名稱、課程說明、課碼及公告，並提供前往成員名單、留言板及作業功能的入口。所有課程成員皆可看到課碼；只有該課程的教師可以看到課碼狀態及執行暫停／恢復課碼操作。對應需求：FR-3.8～FR-3.11、FR-4.7。

#### UI-07 加入與退出課程介面

學生應能輸入課碼加入課程。介面應依第 2.4 節需求顯示加入成功、查無課程、課碼暫停或已在課程中的結果。學生應能對已加入的課程執行退出操作。對應需求：FR-4.1～FR-4.8。

#### UI-08 課程成員頁

成員頁應顯示每位成員的姓名、帳號及身分。教師應能輸入學生帳號，手動將學生加入課程；帳號不存在、帳號不是學生或學生已在課程中時，介面應顯示原因。對應需求：FR-5.1～FR-5.5。

#### UI-09 公告介面

課程頁應依發布時間由新到舊顯示公告。該課程的教師應能發布、編輯及刪除公告；學生只能查看公告。現有需求未定義公告標題、附件或置頂，因此本草稿不新增這些欄位。對應需求：FR-6.1～FR-6.4。

#### UI-10 留言板介面

每門課程應有一個留言板，依發表時間由舊到新顯示單層留言。課程成員可以發表留言；作者可以編輯或刪除自己的留言；教師可以刪除任何留言，但不得編輯他人的留言。對應需求：FR-7.1～FR-7.5。

#### UI-11 作業列表與內容頁

作業列表及作業內容頁應讓課程成員查看作業標題、說明、截止時間、滿分及題目附件。教師應能建立、編輯及刪除作業。對應需求：FR-8.1～FR-8.3。

#### UI-12 作業繳交介面

學生應能選擇檔案並繳交作業。截止時間後仍允許繳交，但介面應標示為「遲交」。學生重新繳交時，新檔案覆蓋舊檔案；截止後重新繳交同樣標記為遲交。對應需求：FR-8.4～FR-8.6。

檔案格式及大小上限目前未在需求獲取階段決定，列於 4.2 待 SD 確認事項，在確認前不得自行加入正式限制。

#### UI-13 批改與成績介面

教師應能查看繳交狀況總表、下載學生繳交檔案、輸入分數及文字評語，並執行發布成績。分數不在 0 到作業滿分之間時，介面應拒絕儲存並顯示原因。學生只有在教師發布後才能看到自己的分數及評語。對應需求：FR-8.7～FR-8.11。

### 3.2 Hardware Interface Requirements（硬體介面）

需求獲取階段沒有形成專用硬體介面需求。本版僅確定系統以桌上型電腦瀏覽器使用，並需要處理作業附件與繳交檔案（D-31、AS-5、FR-8.3、FR-8.4、FR-8.7）。使用者裝置、伺服器及儲存硬體規格由 SD 依架構與部署環境決定，不由 QA 在本草稿中指定。
### 3.3 Software Interface Requirements（軟體介面）

#### SI-01 桌面網頁瀏覽器

系統應透過桌面版網頁瀏覽器提供介面（D-31、AS-5）。實際支援的瀏覽器及版本由 SD 決定，並在 SRS v1.0 簽核前補入 NFR-COM-01 的驗證條件。

#### SI-02 檔案儲存

系統需要保存作業題目附件及學生繳交檔案（DE-3、FR-8.1、FR-8.4、FR-8.7）。實際儲存技術、容量、命名及清理方式尚未由需求獲取決定，由 SD 判斷是否需要形成正式介面或 NFR。

#### SI-03 外部服務

本版本不依賴 Email 或學校帳號系統（DE-1、DE-2），也不提供行事曆、私人訊息、第三方登入或系統管理員後台（D-29）。資料庫產品、框架及其他內部軟體選型屬架構設計，不由 QA 在本章指定（DE-4）。
### 3.4 Communication Interface Requirements（通訊介面）

- 本版本需要支援網頁介面所需的文字資料、操作結果及檔案上傳／下載。
- 瀏覽器與系統之間的實際通訊協定、安全設定及 API 形式尚未由需求獲取決定，由 SD 在架構設計時說明。
- 本版本不使用 Email、即時訊息或其他外部通知通訊協定（D-00a、D-00b、D-18、DE-1）。

## 6. Definitions and Acronyms（名詞定義與縮寫）

### 6.1 Definitions（名詞定義）

**帳號與使用者**

| 名詞 | 定義 |
| --- | --- |
| 使用者 | 已註冊本系統的人，身分為教師或學生其中一種 |
| 帳號 | 使用者登入用的識別碼；學生為學號，教師為教職員編號 |
| 身分 | 帳號的類型，只有「教師」與「學生」兩種，註冊時選擇，之後不可更改 |
| 教師 | 身分為教師的使用者，可以建立課程 |
| 學生 | 身分為學生的使用者，可以加入課程 |

**課程**

| 名詞 | 定義 |
| --- | --- |
| 課程 | 由一位教師建立的教學單位，包含公告、留言板、作業與成員 |
| 課程的教師 | 建立該課程的教師；每門課程只有一位。FR 中寫作「該課程的教師」 |
| 課程成員 | 該課程的教師，以及已加入該課程的學生 |
| 系所代碼 | 2 個大寫英文字母，代表開課系所（例：CS、EE），由教師建立課程時填寫 |
| 課碼 | 學生加入課程用的代碼，格式為「系所代碼 + 7 位數字」（例：CS1234567），由系統自動產生且不重複 |
| 暫停課碼 | 教師將課碼設為無法使用；暫停期間學生無法以該課碼加入課程，教師可再恢復 |
| 退出課程 | 學生自行離開已加入的課程；已繳交的作業與已發表的留言會保留 |
| 成員名單 | 列出課程所有成員姓名、帳號、身分的頁面 |
| 課程列表頁 | 登入後的首頁，列出使用者所屬的所有課程 |
| 課程頁 | 單一課程的頁面，顯示課碼與公告，並可進入留言板、作業與成員名單 |

**公告與留言板**

| 名詞 | 定義 |
| --- | --- |
| 公告 | 課程的教師在課程頁發布的訊息，屬於某一門課程 |
| 留言板 | 每門課程一個的討論區，只有課程成員可以查看與留言 |
| 留言 | 課程成員在留言板發表的一則文字，為單層結構，依時間由舊到新排列 |

**作業**

| 名詞 | 定義 |
| --- | --- |
| 作業 | 課程的教師建立的繳交項目，包含標題、說明、截止時間、滿分、附件 |
| 繳交 | 學生上傳檔案作為作業答案 |
| 重新繳交 | 學生再次上傳檔案，新檔案覆蓋舊檔案；截止時間後重新繳交視為遲交 |
| 遲交 | 在截止時間之後的繳交，系統會加上「遲交」標記 |
| 批改 | 教師對一份繳交給予分數與文字評語 |
| 發布成績 | 教師的操作；按下之後，學生才看得到該作業的分數與評語 |
| 繳交狀況總表 | 列出某份作業每位學生是否繳交、是否遲交、分數的表格，只有該課程的教師可以查看 |

**文件用語**

| 名詞 | 定義 |
| --- | --- |
| 決定表 | 需求決定表（`docs/elicitation-notes/decision-table.md`），記錄需求獲取問卷的結果與 RA 的決定，編號為 D-xx |
| 未來功能 | 本版本不實作、留待之後考慮的功能，見 1.1 |
| 功能描述 | 需求來源標示，指專案的八項核心功能描述（見決定表「八項核心功能」） |
| RA 決定 | 需求來源標示，表示問卷沒有投票、由 RA 依「實作最簡單、先做出可用系統」原則決定 |
| 組內共識 | 需求來源標示，表示經組內討論同意，未經問卷投票 |
| 補充 | 需求來源標示，表示問卷沒有直接問到的項目（多為錯誤處理或邊界情況），由 AI 起草、RA 確認後保留 |
| High / Medium / Low | 需求的優先度；來源為決定表或功能描述者為 High，補充需求的優先度由 RA 個別決定 |
| 滿分 | 作業可得的最高分數，由教師建立作業時設定；教師給的分數須介於 0 到滿分之間 |
